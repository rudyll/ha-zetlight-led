# Zetlight / Horizon Aqua — M5 珊瑚灯通信协议分析

分析对象：Horizon Aqua 64-Bit 安卓版 **4.4.2**（包名 `com.zetlightgoogle`，Zetlight Group），
内部版本串 `Horizon-4.4.2-202610140922_release`，原生 Android（Java/Kotlin），jadx 反编译，类名未混淆。
设备：**M5-80M_AEDC45**，局域网 **10.10.10.138**（Espressif/ESP32）。
目的：本地控制 / 接入 Home Assistant，优先本地、不走厂家云。

> **结论（已实测）：M5 支持本地局域网 UDP 控制，端口 8855，无需蓝牙、无需云。**
> 本机发只读命令已成功读回灯的实时状态，设备码确认为 `01023A01`。这是最佳接入方式。

---

## 1. 三条通道对比

| 通道 | 可用性 | 评价 |
|------|--------|------|
| **局域网 UDP 8855** | ✅ 实测可读可控 | **推荐**：灯联网即可达，HA 直接发包，无距离/广播限制 |
| BLE（服务 00FF / 特征 FF01）| ⚠️ 仅开机瞬间广播，之后 scan 不到 | 不适合常态控制，仅配网用 |
| 云 / IoT（LeanCloud）| 存在 | 不推荐，依赖厂家云、暴露网络 |

BLE 只在上电一瞬广播（实测：拔电重插才出现，几秒后消失），所以靠蓝牙发现→连接不可靠。
好在 App 本来就有本地 WiFi 通道，直接用它。

## 2. 传输层

- **协议**：UDP。App 绑定本地端口、往设备发包、同端口收回包，并开启广播用于发现。
- **端口**：
  - `PORT = 8855`（`BaseUntil.PORT`）——M5 等 LED 设备用这个（老协议 `EE/DD`）。
  - `PORT2 = 8899`（`BaseUntil.PORT2`）——另一套设备/新协议用。
- 发现：往广播地址或直接 IP 的 8855 发查询帧，设备回应自己的信息。
- 源码：`biz/BaseSocket.java`（DatagramSocket，bind/receive/send 到 `BaseUntil.PORT`）。

## 3. 帧格式（老协议 EE/DD + XOR）

```
请求:  EE | 00 | LEN | <设备码4字节> | CMD | <负载...> | XOR | CC
响应:  DD | 00 | LEN | <设备码4字节> | CMD | <数据...> | XOR | CC
```

- 请求头 `0xEE`，响应头 `0xDD`，尾 `0xCC`。
- `LEN`：从"设备码"到"负载末字节"的字节数（不含头/XOR/CC）。两字节 `00 LEN`。
- **设备码（本灯 = `01 02 3A 01`）**：4 字节产品码，来自 `LEDTarget.getChanpingCode()`，
  读命令回包里会原样带回确认。
- `CMD`：命令字节（见 §5）。
- **XOR 校验**：`VerXOR` = 从 `LEN` 高字节(索引1)到负载末字节，逐字节异或。即对
  `[00 LEN 设备码 CMD 负载]` 整体异或，放在 CC 前一字节。
- 尾 `0xCC`。

### 校验算法
```python
def verxor(b):      # b = 帧里从索引1到XOR前一字节(含)
    x=b[0]
    for c in b[1:]: x^=c
    return x & 0xFF
```

## 4. 实测记录（10.10.10.138:8855）

- 发现（新协议广播 `C9000000000A021D`）→ 灯回信标 `DD000F01023A0101 41454443 3435 030400 33 CC`。
- 读灯状态（`EE 00 06 01023A01 0C <XOR> CC`）→ 回：
  `DD 00 1C 01023A01 0C 414544433435 00370037003700370546056E0532051424 CC`
  - 设备码 `01023A01` 确认；名字 `AEDC45`；
  - `0037 0037 0037 0037` = 4 通道当前亮度（各 0x37=55）；
  - `0546 056E 0532 0514` = 4 通道原始/功率值；
  - `24` = XOR，`CC` 结尾。
- **结论：4 通道灯，本地 UDP 可读实时状态，往返正常。**

## 6. 开关实测（已验证 ✅）

2026-10-20 实测：往 10.10.10.138:8855 发下列帧，灯物理上**灭了又亮**，确认有效：

- **关灯**：`EE 00 06 01023A01 1F 21 CC`（CMD 0x1F）
- **开灯/恢复**：`EE 00 06 01023A01 1E 20 CC`（CMD 0x1E，START）

注意：读命令 0x0C 回的 4 通道值是**设定亮度**（setpoint），开/关不改变这几个字节，
所以要判断"当前是否亮着"不能只看 0x0C（需看别的状态字段或直接看灯）。

## 6b. 调光实测（已验证 ✅）

2026-10-20 真机实测确认 0x13 调光帧，`i`/`i6` 两个辅助字节固定为 `0x00`：

```
EE 00 0C 01023A01 13 <i> <c1> <c2> <c3> <c4> <i6> XOR CC
```

- `i` = `0x00`，`i6` = `0x00`（固定）。
- 每通道 `c` = 亮度 BCD：0–99 → `(v//10<<4)|(v%10)`（如 30→`0x30`、55→`0x55`）；**100 特判 `0xAA`**。
- `LEN` = `0x0C`，XOR 规则与其它帧一致（对 `[00 LEN 设备码 CMD 负载]` 异或）。
- 实测帧（均已点亮验证）：
  - 全 10%：`EE 00 0C 01023A01 13 00 10 10 10 10 00 27 CC`
  - 全 100%：`EE 00 0C 01023A01 13 00 AA AA AA AA 00 27 CC`

注意：0x13 是**实时预览**——只改当前输出，不写入设备存储的时间曲线程序。

## 7. Home Assistant 接入方案

**方案（本地 UDP，推荐，最省事）**
- HA 自定义集成直接用 Python `socket` UDP：绑定 8855 → 往 `10.10.10.138:8855` 发
  `EE 00 LEN 01023A01 CMD 负载 XOR CC` → 收 `DD…CC` 回包解析状态。
- **不需要蓝牙、不需要 ESP32 代理**——只要 HA 和灯在同一网段（都在 IoT VLAN 即可；
  跨 VLAN 需放行 10.10.10.138:8855 的 UDP）。
- 实体：`light`（开关+亮度），4 通道可做 4 个 `number` 或合成一个多通道 light。
- 建议给灯配 DHCP 保留地址，避免 IP 变动。

**与 GTS 泵的区别**：泵在 WiFi 上不开端口、只能走 BLE（`[250,…,sum%255]`）；
灯反而 WiFi 本地 UDP 直通（`EE…CC`+XOR）。两者协议不同，但都能纯本地、不碰云。
